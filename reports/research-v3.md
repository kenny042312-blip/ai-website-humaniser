## 2. What the comparison reveals

These conclusions are interpretations of the two instruction sets, not observations of generated-site quality.

**The source makes the offer's argument more explicit.** Humaniser v2 already asks for audience, primary action and decision-critical facts. Elaya adds arrival context, visitor awareness, objections, proof placement, risk terms and a clear separation of page structures. The useful extension is to connect each section to a decision, without requiring fake proof or a fixed number of FAQs. This becomes [landing-page strategy](../references/landing-page-strategy.md).

**Named styles make a visual direction implementable.** Humaniser v2 discusses roles, while Elaya supplies names, scales and repeated-value rules. V3 adds a method to define shared roles once, distinguish visual names from semantic headings, and inspect real wrapping and available weights. It keeps the source's exact tables in an [optional recipe](../references/elaya-visual-recipe.md). A constant theme across all projects would conflict with the user's goal of subject-specific design, so the values remain a chosen concept rather than a universal prescription.

**Finishing details need explicit state and publication checks.** V2 covers primary behavior, errors, empty states and focused application failures. Elaya broadens the checklist to loading, pressed feedback, current navigation, favicon, social previews, forms and not-found views. V3 routes those concerns to the features that actually exist. A static link does not gain fake loading, and a local spacing edit does not trigger a new legal policy or analytics service.

**Aesthetic certainty is not evidence.** Banned fonts, mandatory gradients on headings, irregular sample numbers and a required animated tagline express a style preference. They do not identify authorship or success. The integration preserves the useful optional design information while rejecting those inferences. The source repository's popularity is not used as a quality measurement.

## 4. Technical corrections checked against primary sources

| Issue in the external guidance | Integration decision | Primary source |
|---|---|---|
| The alternative “non indexed path” is left undefined | Specify the actual exclusion mechanism. An unlinked path is not equivalent; a crawler must access a noindex directive to observe it, and robots blocking can prevent this. Privacy still requires access control | [Google noindex](https://developers.google.com/search/docs/crawling-indexing/block-indexing) |
| FAQ schema is suggested for search/AEO | Keep useful visible questions; check current consumers. Google's current changelog records FAQ rich-result removal from 7 May 2026 and documentation removal in June | [Google Search updates](https://developers.google.com/search/updates) |
| requestAnimationFrame is described as scroll throttling | Separate frame scheduling from reducing callback frequency; use actual throttling or suitable observation when needed | [MDN scroll event](https://developer.mozilla.org/en-US/docs/Web/API/Document/scroll_event) |
| Per-word observation is implied to produce a precise scrolling reveal | Distinguish intersection thresholds from continuous per-pixel progress; do not promise the latter from a threshold observer | [MDN Intersection Observer](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API) |
| Reduced motion is universally replaced with opacity | Prefer a readable stable final state; a fade is optional and must not gate content | [MDN reduced motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion) |
| Wrapping properties are treated as an absolute no-orphan guarantee | Treat them as browser-dependent layout tools and inspect real text/fallbacks | [MDN text-wrap](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-wrap) |
| A custom 404 can be confused with an actual not-found response | Check both the recovery view and HTTP status where hosting permits | [Google HTTP status guidance](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes) |
| Social tags can be mistaken for a verified preview | Match real title/type/image/URL, then distinguish metadata checks from observing a consumer preview | [Open Graph protocol](https://ogp.me/) |
| Copying SKILL.md alone into a rules file is suggested for Codex | Keep this skill's references and notices together in a recognized skill folder, preserving an existing installation; a lone entrypoint loses its linked instructions | [OpenAI skill documentation](https://learn.chatgpt.com/docs/build-skills) |

These documentation checks resolve specific integration decisions. They do not expand the rendered design study. Time-sensitive rules should be checked again when a later project actually depends on them.

## 5. Why this may produce more considered work

The following are testable design hypotheses, not measured release outcomes:

1. **Decision sequence:** Matching visitor knowledge, evidence and objections may make a page more intelligible than adding a generic set of marketing sections.
2. **Consistency with variation:** Reusable text and spacing roles may reduce accidental inconsistency while preserving different content forms. A universal font and composition recipe could instead reduce project identity.
3. **Honest completeness:** Working states, truthful terms and real destinations may improve task completion. Manufactured testimonials or waiting indicators only imitate completeness.
4. **Optional expression:** A coordinated visual recipe can speed up a fitting concept; making it optional avoids interpreting one author's taste as a rule for every project.
5. **Accessible persistence:** Visible fallback content, meaningful focus and recoverable states may preserve a design's usefulness under conditions a static screenshot misses.

These hypotheses explain why the changes enter the skill. They do not justify a “human score,” an uplift percentage or a claim that more instructions necessarily improve generation.

## 6. Validation and limits

The [v3 validation record](validation-v3.md) records the actual package checks and a scenario-based instruction review. No independent model generation, controlled v2-versus-v3 website trial, blinded preference study, conversion experiment or screen-reader trial runs for this documentation integration. The existing Low Water behavior is historical implementation evidence, not a new test of v3 output.

The most useful next empirical comparison keeps briefs, source content, tools, viewports and output-review conditions matched; includes a narrow edit, a real landing page with missing proof, a dense dashboard and an opt-in expressive concept; checks task completion separately from preference; and records ties and regressions. This is an evaluation proposal, not a completed result.
